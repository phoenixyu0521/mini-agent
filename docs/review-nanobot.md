# 复盘：nanobot 与 mini-agent 的第一性原理对照

> 时间：2026-10-20 ｜ 对象：`HKUDS/nanobot@main`（`agent/loop.py` 2711 行、`agent/runner.py` 1408 行）
>
> 方法：先写下自己的设计理由，再去看它的做法，只回答一个问题——**它哪几处比我好，为什么。**
>
> 本文所有数字均为本机离线实测（`tests/` 之外的一次性脚本，未调 API）。

---

## 0. 一句话结论

**我的项目在回答「Agent 是怎么运作的」，nanobot 在回答「Agent 怎么才能不死」。**

这两件事共用同一套内核，但目标函数不同。所以它多出来的绝大部分代码，不是「我还没写完」，
而是「它在解另一道题」。判断哪些该学、哪些不该学，标准是：**这条改进补的是原理缺口，还是工程堆料。**

---

## 1. 第一性原理：三个不可回避的问题

大模型是一个无状态函数：文本进，文本出。它不记得上一轮、碰不到文件、不知道自己做完没有。

这条事实推导出全部内核：

| 事实 | 推出的机制 | 我的实现 | nanobot 的实现 |
|---|---|---|---|
| 它不记得 | 每轮重新组装 `messages` | `self.messages` + `_view()` | `TranscriptInput` + `ContextGovernor` |
| 它碰不到世界 | 工具协议（声明 → 执行 → 回填） | `tools/` + `registry.call()` | `tools/` 36 个文件 + `execution.py` |
| 它不知道做完没 | 循环 + 终止判据 | `_run_tool_rounds` + `max_iterations` | `AgentRunner._run_core` + `stop_reason` |

**三家（我、nanobot、ROADMAP）在这张表上的结构是一致的。** 这说明内核判断没错。
差异全部出现在第四层——**当这个函数被放进一个真实的、会崩溃、会有多个人同时用的世界之后。**

---

## 2. 两个项目的目标函数不同

| 维度 | mini-agent | nanobot |
|---|---|---|
| 根本目的 | 让一个人**看懂**三个问题 | 让一个进程**长期活着**且不出错 |
| 首要约束 | 可理解性 | 可靠性 / 不重复副作用 |
| 复杂度预算 | 753 行一个类 | 2711 + 1408 行，两层 |
| 失败代价 | 学习者困惑 | 用户数据错乱、工具被重复执行、消息丢失 |
| 成功判据 | 每一处能讲出「为什么」 | 24×7 无人值守、18 个渠道 |

**关键判断：这不是完成度差异，是目标函数差异。**

所以「把 nanobot 的功能逐条补上」是错的——那是把学习项目改造成半成品工业软件，
既得不到工业级的可靠性（缺测试、缺监控、缺运维），又毁掉了学习项目最大的价值（每一行都能解释）。

正确的做法是：**只补那些「不补就说明原理没想透」的缺口。**

---

## 3. 三个真实缺口（都有实测数字）

### 3.1 裁剪判据用了一个错误的代理指标

`context.needs_compaction()` 判断的是**条数**：

```python
return len(messages) - 1 > threshold      # COMPACT_AT = 12
```

但模型的真实约束是 **token 窗口**。条数只是它的一个粗糙代理。

实测（`estimate_tokens` 是我自己写的函数，1 token ≈ 2 字符）：

| 场景 | 条数 | 估算 tokens | 是否压缩 |
|---|---|---|---|
| A：5 轮，每轮 4 万字符 | 11 | **100,001** | **否** |
| B：20 轮，每轮 2 字符 | 41 | **41** | **是** |

A 会把 10 万 token 直接发出去（很多模型窗口就是 128k，再加工具说明书就撞墙）；
B 白花一次摘要请求，把 41 token 的历史「压缩」成一段摘要。

**这就是「偶尔莫名其妙的 HTTP 400」的根源：用代理指标代替真实约束。**

更狠的证据在第二层。我造了一条 30 万字符的 `tool` 消息，跑一次 `compact()`：

```
原始: 条数=26  tokens≈151034
视图: 条数=10  tokens≈151027     ← 压掉 16 条，只省了 7 个 token
视图里那条 tool 还在吗: True
```

**压缩动作执行了、摘要请求花钱了、结果几乎为零。** 因为保留区只保证「最后 8 条」，
不保证「这 8 条总共多大」。

nanobot 的做法是两层：

- **判据用预算**：`budget = context_window_tokens - max_output - CONTEXT_SAFETY_BUFFER`
- **单条也有天花板**：工具结果超过 `max_tool_result_chars` 时**落盘**，
  上下文里只放「文件路径 + 头尾预览」（头告诉你这是什么，尾通常是错误信息或结论）

后者比「直接截断」高明：**信息没丢，只是从上下文搬到了磁盘。** 模型需要时可以再读一次。
这叫外置内存，不叫丢弃。

### 3.2 刹车只负责停车，不负责收尾

`max_iterations` 跑满时，我返回的是一句固定文案：

```python
sink["text"] = f"已达到最大工具调用轮数（{max_iterations}），我先停在这里。"
```

实测（假模型，每轮都要求调工具）：

```
返回给用户: '已达到最大工具调用轮数（5），我先停在这里。'
本轮工具调用次数: 5
messages 里现有 tool 结果条数: 5
```

**5 条工具结果都在上下文里，但用户一个字都拿不到。** 前面四轮查询全部白做。

nanobot 的 `_try_finalize_after_max_iterations()` 做的是：撞上限后**再发一次不带工具的请求**，
提示模型「预算用完了，用你手上已有的信息给出结论」；这次也失败，才退回模板文案。

原理上的区别：

> **上限的作用是「阻止继续行动」，不是「丢弃已经取得的成果」。**
> 一个只会急刹车的 Agent，和一个会靠边停车的 Agent，差别不在速度，在可用性。

这个改动很小——一次 `llm.chat(view)` 不带 `tools` 而已。

### 3.3 崩溃会重放副作用

我的落盘时机是「每轮工具循环结束后 `flush_session()`」。中间有一个窗口：

```
执行 run_shell("rm build/ -rf")  →  ✅ 副作用已发生
                                  ↓  ← 进程在这里崩了
写 tool 结果消息                  →  ❌ 没写进去
```

重启后模型看到的对话是「我说过要删，但没有结果」。它会**再删一次**。
对只读工具无所谓，对有副作用的工具这是安全问题。

nanobot 在三个时刻写 checkpoint：`awaiting_tools`（已声明、未执行）、`tools_completed`（已执行、未回填）、
`final_response`。并且在保存时校验 `tool_call_id` 配对——没有对应 assistant 声明的 tool 消息、
重复的 `tool_call_id`，一律丢弃。

原理上的区别：

> **持久化的目的不是「保存聊天记录」，是「让重启后的世界与崩溃前一致」。**
> 前者关心内容，后者关心**执行状态**。

这条是「demo」和「能长期跑的东西」之间真正的分水岭。实现成本中等（执行前写 pending 标记、
执行后写结果），概念价值极高。

## 4. 两处「该学结构，不该照抄手段」

### 4.1 工具分批：按原顺序切段，而不是整批退化

我现在的策略是：**全批都是只读工具才并行，否则整批串行。**

当时的推理是：

> 不能把安全的挑出来提前跑——模型说「先跑命令，再读结果文件」，你把 read_file 提到前面，
> 读到的就是旧内容。

这个担心是对的，但结论下早了。nanobot 的 `_partition_tool_batches()` 给的是第三种答案：

```
[read, read, shell, read]
   ↓ 按原顺序切段
[read, read] 并发  →  [shell]  →  [read]
```

**批次之间严格串行，批次内部并发。** 既没有提前任何工具，也没有让混合场景全部退化。

我漏掉的是「切段」这个动作——把「顺序」理解成了「必须整体保持」，而不是「段与段的相对次序保持」。

⚠️ 但有一处**不能照抄**：nanobot 用 `asyncio.gather`，因为它的工具全是 `async def execute()`
（有网络、MCP、子进程）。我的工具是同步阻塞函数，`gather` 对它们无效，必须线程池。
**结论相同（并发），手段不同，因为前提不同。** 这是这次复盘里最值得记住的一条方法论。

顺带一个小发现：nanobot 的并发资格不是一个布尔值，而是两个正交属性推导出来的——

```python
read_only      # 有没有副作用
exclusive      # 即使只读，是否必须独占（限速 API、正在被写的文件）
concurrency_safe = read_only and not exclusive      # 默认 False
```

我的 `concurrency_safe` 把「有副作用」和「不能同时跑」压成了同一件事。
表达能力上少了一档：**一个只读但需要独占的工具，在我这里无处安放**（只能标 False，并连带拖慢整批）。

### 4.2 分层：`loop` 管编排，`runner` 管执行

nanobot 的 `AgentRunner` 开头一句 docstring 就说明了边界：

> Run a tool-capable LLM loop **without product-layer concerns**.

它靠一个纯数据 `AgentRunSpec` 进、一个 `AgentRunResult` 出。中间的会话、磁盘、渠道一概不知道。
`AgentLoop` 负责的才是：消息从哪来、存到哪、什么时候允许插话、命令怎么分发。

我的 `AgentLoop` 753 行一个类，同时管 session、memory、metrics、工具循环、流式输出。
**收益不在「代码好看」，在可测试性**：拆完之后，内核可以用「假 messages + 假 provider」直接测，
不用建目录、不用打桩 `Session`。

但这一步**现在不建议做**。原因是：拆分层要在接口稳定之后，而我的下一步很可能是加 MCP 或子 Agent——
那会重新定义 `Spec` 的字段。现在拆，等于拆两次。

## 5. 我做对了、不该改的地方

复盘不能只写「它比我强」。有三处我有明确理由保留：

1. **注释即设计文档。** nanobot 的注释写给维护者（解释这段代码在防什么），
   我的注释写给学习者（解释这个决策为什么这么下）。后者是学习项目唯一的护城河。
2. **三段耗时归因（prepare / model / tool）。** nanobot 的 `turn_stage` 记的是流水线阶段
   （restore / compact / build / run / save / respond），**它不区分「等网络」和「跑本地工具」**。
   我的切法更适合回答「这次为什么慢」——因为模型等待是秒级，本地工具是毫秒级，混在一起平均等于没测。
   这是两个不同切面，不是谁更先进。
3. **fail-closed 的默认值。** `concurrency_safe` 默认 `False`、路径检查先拒后放、
   白名单优于黑名单。nanobot 靠更厚的策略层（workspace policy + sandbox + SSRF 白名单）达成同样目的，
   我的更小，但边界更清楚。

## 6. 改进优先级

### 必做（原理级缺口，各自 20–60 行）

| # | 改什么 | 为什么是原理级 | 验证方式 |
|---|---|---|---|
| 1 | `needs_compaction` 改用 token 预算 | 用代理指标代替真实约束，是所有静默撞墙的根源 | 复现 11 条 10 万 token 不压缩 |
| 2 | 工具结果加体积上限（超长落盘 + 引用） | 「上下文是稀缺资源」必须落到单条消息上 | 读 1MB 文件，看视图 token |
| 3 | `max_iterations` 撞上限时做一次无工具收尾 | 上限该阻止行动，不该丢弃成果 | 跑满 5 轮，检查返回里有没有内容 |
| 4 | 执行前写 pending、执行后写结果（checkpoint） | 持久化的对象是执行状态，不是聊天记录 | 杀进程后重启，看工具会不会重跑 |

### 知道就好（工程级，先不做）

- 中途插话（`_drain_injections`）：长任务/多用户才需要，它解释了 nanobot 循环里为什么到处是 drain。
- `provider_state` 原生续传：特定厂商能力（prompt cache / previous_response_id），换厂商就失效。
- usage 估算兜底：我只在上游不给 usage 时记 0，会让成本指标失真，但影响面小。
- 子 Agent 委派、技能系统、MCP：属于「分叉决策」之后的方向，不是复盘结论。

### 明确不做

- **不建议现在拆 `loop` / `runner`。** 接口未稳定，拆了要拆两次。
- **不建议把工具改成 `async def`。** 现有工具没有真异步 I/O，改了只是把线程池换成更复杂的东西。

### 如果只改一处

**改 #1（token 预算）。** 它是唯一一个「不报错、只是偶尔崩」的缺口，
也是唯一一个能同时改善成本和稳定性的改动。改动点集中在一个函数：

```python
def needs_compaction(messages, budget=...):
    return estimate_tokens(messages) > budget
```

`estimate_tokens()` 已经写好了，只是没被用在判据上——**零件齐了，没接线。**

## 7. nanobot 比我强的三点（ROADMAP 要求的那一页）

1. **它用真实约束做决策，我用代理指标。** token 预算 vs 条数；工具结果按字符落盘 vs 无上限。
   代理指标在多数时候够用，代价是「偶尔毫无征兆地失败」——而生产的可靠性恰恰由那 1% 决定。
2. **它的每条失败路径都有「下一步动作」，我的多数只有「一句话」。**
   空回复 → 重试 → 无工具收尾；坏 tool_call → 丢弃重试 → 无工具收尾；
   撞上限 → 收尾请求 → 模板兜底。**可靠性不是「不出错」，是「出错之后还有路」。**
3. **它持久化的是「可恢复的执行状态」，我持久化的是「聊天记录」。**
   三阶段 checkpoint + `tool_call_id` 配对校验，让「重启」等价于「暂停后继续」，
   而不是「重来一遍，顺便把副作用再来一次」。

这三点其实是同一件事的三个面：

> **我的代码假设一切顺利，它的代码假设每一步都可能失败。**
